## 1. Что это

Eskiz Oyna — приложение для оконщиков: замер на объекте, конструктор окон и дверей, расчёт по реальным материалам, КП клиенту и документы для цеха. Часть семейства Eskiz (Mebel, Temir, DWG, Lavha) с общим аккаунтом, оплатой и брендом.

**Конкурент — Romchi.** Он берёт 79 000 – 624 000 сум за расчёт и КП и при этом не проверяет конструкцию: в нём можно собрать окно 9 км × 10 см. Наша стратегия — отдать бесплатно то, за что Romchi берёт деньги, и зарабатывать на производственной части, команде и ИИ.

**Ключевое отличие:** расчёт по реальной спецификации (длины профилей, раскрой, стеклопакеты, фурнитура по размеру створки) и инженерные проверки, которые ловят брак до сметы.

## 2. Цели и не-цели

**Цели MVP**
1. Замерщик собирает типовое окно на объекте за 1–2 минуты, без бумаги.
2. Клиент получает КП с ценой в Telegram до ухода замерщика.
3. Расчёт совпадает с реальной ценой цеха в пределах ±5% на 3–5 эталонных заказах.
4. Невозможные и опасные конструкции блокируются до сметы.
5. С приложением можно прийти к поставщикам профиля и цехам за их каталогами.

**Не цели MVP**
- Приём оплат в приложении (Payme, Click, предоплата) — не делаем вообще.
- Склад, бухгалтерия, CRM-воронка.
- Фотореалистичный рендер.
- Размеры с фото — размеры всегда вводит человек.
- Сторона конечного клиента, кроме страницы КП по ссылке.

## 3. Пользователи и роли

| Роль | Задачи | Не видит |
| --- | --- | --- |
| Владелец цеха | Настройки, наценка, комплектации, цены, сотрудники, все заказы | — |
| Менеджер | Заказы, КП, скидка до лимита (больше — запрос владельцу) | Себестоимость (настраивается) |
| Замерщик | Мастер замера, цена для клиента, отправка КП | Себестоимость, наценку |
| Монтажник | Свои монтажи, монтажный лист, фото, акт | Цены |
| Производство | Лист для цеха, раскрой, статус «готово» | Цену клиента |

**MVP:** владелец и замерщик. Остальные роли — платная «Команда».

**Режимы цеха:**
- «Сам варю окна» — расчёт по материалам.
- «Заказываю у производителя» (дилер) — себестоимость = материалы × (1 + коэффициент производителя), сверху своя наценка; заказ уходит производителю PDF или ссылкой.

## 4. Принципы

1. **Ядро считает, ИИ только помогает вводить.** ИИ вызывает те же команды, что и редактор; не меняет цены и не обходит блокирующие правила.
2. **Одно дерево изделия** для шаблонов, редактора, мастера замера и ИИ.
3. **Расчёт на сервере.** Ядро `oyna_core` на Python рядом с `mebel_core`. Себестоимость не уходит на телефон, прайсы и правила обновляются сразу у всех.
4. **Замер работает без сети.** Схема рисуется на телефоне, замер хранится локально и синхронизируется при появлении сети. Без сети вместо цены — «посчитаем, когда появится интернет».
5. **Неполная цена не уходит клиенту.** Если у позиции нет цены — КП не отправляется. Исключение — демо-цех (`demo_prices`): там вместо пустой цены берётся ДЕМО-цена, предупреждение D.1 и метка «ДЕМО» на КП; у настоящих цехов режим выключен.
6. **Предупреждения можно принять**, это фиксируется (кто, когда) и попадает в лист для цеха.

## 5. Архитектура

| Слой | Технология |
| --- | --- |
| Мобильное приложение | React Native + Expo (как Eskiz Mebel); iOS и Android, тестировать на дешёвом Android |
| Веб для офиса | Next.js, домен в семействе Eskiz |
| API | FastAPI |
| Ядро | Python-модуль `oyna_core`: модель, команды, правила, спецификация, раскрой, цена, рендер SVG/GLB |
| ИИ | `oyna_ai` на Claude, только через команды ядра (tool calls) |
| База | PostgreSQL (схема — `oyna_data/schema.sql`), Redis для очередей и кэша расчёта |
| Файлы | S3-совместимое хранилище: фото проёмов, PDF, GLB |
| Вход | Телефон + SMS (общий аккаунт Eskiz) |

**Поток расчёта:** клиент меняет дерево локально → после паузы ввода ~0,5 с отправляет позицию на сервер → сервер возвращает нарушения правил, спецификацию и цену → клиент подсвечивает ошибки и показывает цену.

**Офлайн:** мастер замера и редактор пишут изменения в локальную базу (SQLite/MMKV) с ревизией; синхронизация последним-побеждает на уровне позиции, конфликт — показать обе версии.

## 6. Модель изделия

Изделие — один JSON-документ (`order_positions.doc`). Расчёт в нём не хранится, всегда пересчитывается; замораживается только в версии КП.

```json
{
  "id": "pos_01",
  "room": "Кухня",
  "qty": 1,
  "kind": "window",
  "opening": {"width": 1440, "height": 1340, "wall": "brick", "quarter": false,
              "slope_depth": 250, "nearby": []},
  "setup": {"system": "akfa__6000_qvt", "profile_color": "white", "lam_out": "golden_oak", "lam_in": null,
            "glass": "g4_12_4", "fittings": "fornax",
            "options": {"handle": "euro_pvc.tilt_turn.handle_hoppe_hamburg"}},
  "frame": {
    "w": 1400, "h": 1300, "shape": "rect",
    "root": {
      "split": "v",
      "parts": [
        {"size": "eq", "cell": {"type": "sash", "open": "tilt_turn", "hinge": "left", "handle": true, "mosquito": true}},
        {"size": "eq", "cell": {"type": "fixed", "fill": {"kind": "glass", "glass": "6t-12-4"}}}
      ]
    }
  },
  "extras": {"sill": {"depth_cm": 30}, "drip": true, "slopes": true, "dismantle": "wood"},
  "accepted_warnings": []
}
```

- **Узел дерева** — либо деление (`split`: `v`, `h`, `shtulp`, `none`; список `parts`), либо ячейка (`cell`). Между частями `v`/`h` автоматически стоит импост; `shtulp` — две створки без импоста; `none` — части без профиля между ними: в редакторе такое не собрать, но может прийти из ИИ или импорта, и правило 6.1 его блокирует.
- **Часть деления** — `{"size": …, "cell": {…}}` или `{"size": …, "node": {"split": …, "parts": […]}}` для вложенного деления (шаблоны T07, T09).
- **Форма рамы** — `frame.shape` (`rect` | `arch` | `circle` | `trapezoid` | `bevel` | `triangle`) + `frame.shape_params` (`docs/shapes_contract.md` §1). Дерево делится прямоугольниками, ячейка = прямоугольник ∩ контур; фигурная ячейка — `shaped`, контур `poly`. Профиль — по длине контура, гнутая часть — работа «гибка» (`work_bend`), стекло — по площади контура + `shaped_extra_pct`. Старая запись T16 (`root.shape`, `rise_mm`) читается как `frame.shape`.
- **Составное изделие** — `kind: "assembly"`, `frame.root.assembly = [рама, стык, рама, …]` (угловые, эркеры, витражи, лоджии; §4). Стык: `straight` | `angle` (90…179°) | `post`. Каждая рама считается как окно без монтажа, плюс соединители по высоте стыка; монтаж один на сборку. Пути ячеек — `A<i>/…`.
- **Раздвижные** — корень `{"sliding": {"leaves", "rails", "overlap_mm", "moving", "kind": window|door|panoramic, "threshold"}}`. Считаются с 2026-11-20 (`docs/shapes_contract.md` §11.1): полотна равной ширины с перехлёстом по паспорту, роли `sl_*`, угол без стойки — стык `corner_free`.
- **Гильотинное окно** — узел `split: "vslide"` (два полотна сверху вниз, `slide`, `tilt_clean`), роли `vs_*` (§11.2).
- **Гильотина для террас** — `kind: "guillotine"`, корень `{"guillotine": {"modules", "panels", "moving", "drive", "glass", "posts"}}`, роли `gl_*` (§11.3). Павильоны и зимние сады — не в Oyna (металлоконструкция → Eskiz Temir).
- Раздвижные и гильотина по умолчанию на ДЕМО-системе «Раздвижная алюминиевая» (`eskiz__sliding_demo`), пока у цеха нет своей.
- В `templates.json` дерево лежит в `root` шаблона; в изделии — в `frame.root`, габарит — в `frame.w/h` (у шаблона — `default_w/h`).
- **Размер части** — число мм (зафиксировано) или `eq` (поровну из остатка). Размеры по осям импостов.
- **Ячейка:** `fixed` | `sash` | `door_sash` | `panel`. Створка: `open` = `turn` | `tilt_turn` | `tilt` | `sliding` | `top_hung` (подвесное) | `pivot` (среднеподвесное); `hinge` = `left` | `right` | `top` | `bottom`; `handle`; `mosquito`. Раскладка — `cell.muntins` (`inner` / `overlay`, `grid` / `sun` / `cross` / `decor`; §2). Двери и порталы (§9.1): `open` = `folding` (гармошка, `split: "folding"`) | `psk` | `hs`; `open_dir` = `in` | `out`; `threshold` = `standard` | `low_alu` | `none`. Сетка `mosquito` = `true` | `{type: frame|sliding|pleated|door|antipet}` (§9.2), приточный клапан `vent` (§9.4).
- **Добавки изделия** (§9.3–9.7): `addons` (расширители, подставочный, соединитель коробок, нащельник, козырёк), `shutter` (рольставня / жалюзи), `grille` (решётка), `loggia` (вынос, крыша, обшивка), `custom_lines` (своя строка цеха, `no_markup`). В `setup` — ещё `seal_color` (`black` | `grey`) и `bead` (`square` | `round` | `profiled`).
- **kind:** `window` | `balcony_block` | `door` | `sliding` (рама + N створок на направляющих) | `assembly` (несколько рам + соединители).
- **setup** — комплектация; смена комплектации меняет только это поле.
  - `system` — серия профиля; `fittings` — набор фурнитуры (`fitting_systems.json`), доступный только при совместимом пазе.
  - `profile_color` — цвет профиля в массе (`profile_colors.json`), `lam_out` / `lam_in` — ламинация по сторонам (`decors.json`), видимый цвет стороны — `side_color()`; ценовая группа прайса вычисляется. Старые `color_out` / `color_in` читаются как ламинация (§8).
  - `glass` — пресет (`g4_12_4`) или своя формула (`6t-14-4i`, грамматика в `glass_formula.json`).
  - `options` — выбранные варианты деталей по группам (`handle`, `hinge`, `security`, `extra_lock`); не указано — вариант по умолчанию.
- **Ячейка может переопределить комплектацию:** `cell.fill` — `{"kind": "glass", "glass": …, "decor"?: matte|tinted|mirror|pattern|stained}` | `{"kind": "panel", "item": "lambri"}` (другое стекло, декор стекла или панель только в этой ячейке); `cell.options` — свои варианты деталей для этой створки.
- Шаблоны в том же формате — `oyna_data/templates.json` (50 шт., с `category` и `short`; фигурные — с `shape` / `shape_params`).

## 9. Формулы

Все параметры — из паспорта системы (`passports.json`; сейчас ДЕМО). Поля: `bf`, `bi`, `bs` — видимая ширина рамы/импоста/створки; `ov` — заход створки; `weld` — припуск на сварку на конец (алюминий — 0); `imp_add` — добавка импоста на заход в раму; `g` — зазор под стеклопакет на сторону; `r` — заход стеклопакета в фальц; `bar` — длина хлыста; `cut` — ширина пилы.

- Рама: `L_гор = W + 2·weld`, `L_верт = H + 2·weld`.
- Импост: длина в свет между профилями + `2·imp_add`.
- Створка: `W_ств = W_свет + 2·ov`; профиль `L = W_ств + 2·weld`.
- Стеклопакет: `W_сп = W_свет_контура + 2·r − 2·g`; расчётная площадь `max(W·H, S_min)`.
- Вес створки: `m = S_ст · t_ст · 2,5 + P_ств · q_пр` (правило 3); сравнение с пределом фурнитуры.
- Армирование ПВХ: длина профиля минус отступ от углов; по правилам 5.1–5.3.
- Штапик: периметр стеклопакета; тип по толщине (паспорт → `beads`).
- Уплотнитель: периметр створок + периметр стеклопакетов × 2, в метрах; кг = м / норма (20–30 м/кг, `consumables.json`).
- Соединители импоста: 2 на импост.
- Подоконник, отлив: `W + 2 × выступ`; откосы: `2H + W`.
- Фурнитура: правила `fitting_rules.csv` по типу открывания и размеру створки по фальцу.
- Итог: `C = Σ материалы + Σ работы`; `P = round₁₀₀₀((C · (1 + m) или C + m_м² · S) · (1 − d))`.

## 10. Команды ядра (API)

## 14. Нефункциональные требования

- Пересчёт позиции на сервере ≤ 300 мс на типовой позиции; ответ клиенту после паузы ввода ~0,5 с.
- Мастер замера и редактор работают без сети; ни один шаг замера не теряется при закрытии приложения или севшем телефоне.
- Тестирование на дешёвом Android (2–3 ГБ ОЗУ); схема — 2D SVG, 3D только по кнопке.
- Себестоимость и наценка не отдаются в API для ролей без доступа.
- Все правила, паспорта и правила фурнитуры — данные в базе, а не код; меняются без релиза.
- Детерминированность: одинаковые изделие + версия прайса → одинаковая цена.
